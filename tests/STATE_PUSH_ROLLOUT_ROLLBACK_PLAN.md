# CU / emart24 / GS25 state-push rollout and rollback review

**Status: REVIEW ONLY — NOT DEPLOYED.** Source: isolated branch `emart24-p0-isolated-test`; production workflows, `main`, `emart24-recovery`, PR #1 and operational state files remain untouched.

## Decision: NO-GO until blockers are resolved

1. `tests/state_push_retry_candidate.py` allowlists three state files, but emart24's `stock-monitor.yml` also persists `stores.json`. A deployment that omits that cache changes existing behavior. Design and test a two-file, same-run emart24 artifact transaction or explicitly approved separate cache writer.
2. The candidate `state_at()` uses `git show` decoded as text then re-encoded as UTF-8. Preserve byte-level JSON equivalence and distinguish missing files from Git errors.
3. The candidate uses a clean disposable checkout and `git reset --hard FETCH_HEAD`. It MUST NOT run in the scan checkout: state generated by the scan would be erased. Use a distinct checkout and a validated artifact outside that checkout.
4. Current test helper permits a same-chain remote state equal to the artifact. That should be idempotent; a differing same-chain state must fail closed. Define recovery of skipped state writes before deploying.
5. The candidate contains an incorrect-looking staged-diff check; independently verify both the unchanged-state path and the changed-state commit path. A successful no-op must not mask a changed-but-unpushed state.
6. Test isolation: the candidate integration tests currently permit local `file://` Git transport; ensure production network/Telegram credentials are absent and that only temporary bare repositories are used.

Avoid automatically treating all failures as a valid state update.

## Artifact transfer contract

- Scan job records its starting `github.sha` / checkout SHA as `base_sha`, plus chain, run ID, attempt, schema version, and a SHA-256 checksum per file.
- Scan job writes to a temporary staging directory, not to a Git commit; upload with `actions/upload-artifact` using unique names `stock-state-<chain>-<run-id>-<run-attempt>`. Avoid publishing secrets.
- Publish job depends on scan job and downloads only that run's artifact with `actions/download-artifact`; verify path allowlist, JSON structure, checksum, chain and base SHA before touching Git.
- Publish job uses a **fresh disposable checkout**, with a narrowly scoped write token; the scan job must not receive a write token if it does not need one.
- Publish only this chain's allowed paths. For emart24, handle `state.json` and `stores.json` consistently in one candidate commit, subject to independent validation.
- Fetch current main; compare each remote path against scan base. If the same chain has changed, fail closed unless a reviewed merge policy allows it. Never blindly replay stale stock.
- On non-fast-forward rejection, fetch/revalidate/reapply, with at most 3 attempts and backoff. Never repeat stock API calls or Telegram sends in the publisher.
- Upload artifacts are short-lived and should have a defined retention period. Failed publication must be observable and actionable, not silently ignored.

## Workflow policy / GitHub Actions caveats

- The existing groups (`cu-stock-monitor`, `pokemon-stock-monitor`, `gs25-stock-monitor`) serialize within each chain, **not across chains**.
- A common concurrency group across *whole workflows* would delay scans. A common group on *publisher jobs* reduces but does not replace optimistic conflict handling.
- Evaluate `needs`, `if: always()`, partial-failure policies, and `timeout-minutes` carefully: if the scan fails, an artifact may still contain valid partial GS25 results; the emart24 all-unknown state must not be published.
- The publisher must not use `git add -A` or commit any files except its explicit allowlist.
- A race can occur between fetching `main` and pushing; bounded retries remain necessary.

## Proposed staged rollout after explicit approval

1. Finish tests and candidate changes in the isolated branch, leaving operational YAML untouched.
2. Create a separate approval PR containing only the agreed helper and workflow modifications. Review diff, permissions, secrets and test logs.
3. Enable one chain at a time (CU, then GS25, then emart24), verifying successful state writes, alert behavior, no duplicate notifications, and no cross-chain state loss.
4. Keep a pre-deployment tag/SHA and documented rollback command for the workflow changes.
5. Roll back immediately on missing artifacts, stale-state conflict loops, unexpected state resets, or Telegram side effects. Roll back code/workflows only; **do not blindly roll back state JSON** because it could erase legitimate newer observations.

## Rollback runbook (approval required)

1. Disable only the newly introduced publisher jobs or revert the approved workflow/helper commits to the pre-rollout SHA; avoid force-push.
2. Restore the previous scan/save workflow behavior using a new revert commit, not by resetting `main`.
3. Inspect latest successful state commits and compare all four state/cache files before any manual recovery. Never overwrite a newer valid stock baseline.
4. Review failed publication artifacts, check run ID, chain, checksum and base SHA, then replay **state publication only** if still valid. Never rerun Telegram as part of recovery.
5. Validate all three monitors and document the rollback decision and remaining unpublished states.
