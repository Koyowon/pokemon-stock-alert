## 결론

현재 이마트24의 직렬 조회 뒤 고정 1.5초 대기가 가장 큰 코드상 지연이다. 이를 요청 시작 간 최소 1.5초 간격으로 바꿔 응답 대기 시간을 간격 계산에 포함시켰다. 동시에 진행하는 요청은 여전히 1개, 묶음은 검증된 기존 3점포이며 전체 183점포를 유지한다. API의 더 큰 묶음이나 병렬 허용량은 확인되지 않아 도입하지 않았다.

실제 감지 간격은 코드 실행시간보다 GitHub 예약 시작 간격의 영향을 크게 받는다. 이번 표본에서 재고 모니터의 실제 예약 시작 간격은 약 17~34분이었다. 5분 cron이라고 5분 감지가 보장되는 것은 아니다. 이 변경만으로 초 단위 감지나 확정된 최소 조회시간을 달성한다고 주장하지 않는다.

## 구현한 개선

1. 이마트24 요청 페이싱: 응답 뒤 항상 1.5초를 더 기다리는 방식에서, 실제 요청 시작 간격 최소 1.5초를 유지하는 방식으로 변경했다. 마지막 응답 뒤 불필요한 대기도 제거했다. 요청 수·직렬 처리·3점포 묶음은 유지하지만 평균 요청률은 기존보다 높아질 수 있다. 서비스의 공식 허용 요청률을 확보한 것은 아니다.
2. 이마트24 장애 시 먼저 최대 3개 배치를 확인한다. 전면 장애에는 6번의 단일 점포 재시도를 하지 않는다. 정상 배치가 있고 회로가 열리지 않은 부분 실패에만 마지막에 최대 6개 단일 점포 복구를 시도한다. 연속 3실패 후 남은 점포는 미확인으로 유지한다.
3. CU·GS25·CU 상품등록은 연속 3번 논리 조회 실패 후 그 실행의 남은 조회를 중단한다. 성공한 조회는 실패 연속 수를 초기화한다. 400/401/403/404/429 HTTP 응답은 즉시 추가 조회/재시도를 중단한다. 이마트24도 같은 HTTP 처리를 적용한다. 회로는 실행 간 영구 저장하지 않으며 다음 정기 실행에 다시 시도한다.
4. 이마트24 매장 검색 실패 후 last_refresh_attempt를 저장하고 15분간 동일 검색을 반복하지 않는다. 재고 조회는 계속한다. 기존 매장 목록과 last_refresh 성공 시각은 보존한다. 동적으로 새로 발견되는 점포의 재검색이 최대 15분 늦어질 수 있다.
5. 동일 입력 점포코드·좌표·키워드를 순서 보존 방식으로 중복 제거했다. 다른 좌표나 다른 검색어가 반환한 중복 매장은 기존 충돌/주소 검증을 유지한다. 검색 범위와 검증된 기존 좌표는 줄이지 않았다.

## 예약 주기와 최소 시간의 한계

현재 재고 cron은 이미 5분 간격이고 CU 상품등록만 15분이다. 승인안은 cron과 Actions를 수정/실행하지 않는다. GitHub 공식 문서상 schedule 최소 간격은 5분이며 부하에 따라 지연되거나 실행이 누락될 수 있다.

- https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule
- https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule

현재 예약 누락/간격 증가의 개별 원인을 이 실행 목록만으로 확정할 수 없다. 확정적인 짧은 주기를 원하면 별도 상시 실행 호스트·작업 잠금·API 호출 예산·재시작/저장 방식을 정해야 한다. 여기서는 새 서버를 배포하거나 비용을 발생시키지 않았다. 1초/10초 반복이나 미검증 병렬화를 적용하지 않았다.

## 승인 대상

이 브랜치의 검증된 코드 개선만 main에 반영하는 승인을 요청한다. 점포·상품·좌표·기존 상태·알림 조건·예약 주기는 유지한다. 운영 반영 뒤의 실제 속도는 이후 기존 예약 실행 기록으로 확인할 수 있다. 수동 재고 조회·Telegram 테스트·Actions dispatch는 승인 대상에 포함하지 않는다.

## 되돌리기

승인 후 반영한 최적화 커밋의 코드 파일만 되돌린다. 그 사이 누적된 재고/Telegram 상태 파일과 점포 등록 데이터는 되돌리지 않는다. GitHub 브랜치 보호나 쓰기 충돌이 있으면 강제 push하지 않고 최신 변경과 대조한다.
