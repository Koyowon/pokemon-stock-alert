# 세븐일레븐 수량 확보 경로 재점검

## 확인된 사실

21:04 KST 운영 실행은 아산시 조회 TRANSPORT_ERROR와 아산배방점 UNVERIFIED_RESPONSE 뒤 호출을 중단했다. 기존 로그에는 세부 검증 사유가 없어서 이 개별 응답이 왜 검증에 실패했는지는 확정할 수 없다.

이전 진단에서 전주시 전체 요청은 약 34초 뒤 정상 응답한 사례가 있었다. 운영 소켓 타임아웃 20초는 이 응답을 받기에 부족하다. 다만 이번 45초 타임아웃의 제한된 실제 재확인도 다음처럼 모두 HTTP 502였으므로 타임아웃만 바꾸면 수량을 반드시 확보한다고 볼 수 없다.

| 실제 요청 | 결과 | 소요 시간 |
|---|---|---:|
| 전주시 전체 / limit 200 | HTTP 502 | 36.38초 |
| 남원시 전체 / limit 200 | HTTP 502 | 6.66초 |
| 전주팔복프라임점 / limit 5 | HTTP 502 | 7.22초 |

원본 오류 본문은 CONVENIENCE_RELAY_FAILED, operation=seveneleven_request, upstreamStatus=502다. 공개 제3자 릴레이의 실패를 확인한 것이며 세븐일레븐 공식 원천 시스템의 내부 원인은 확인하지 않았다. 임의 수량을 기록하지 않았다. 실제 조회는 이번 진단 3회로 종료했고 Telegram·Actions 수동 실행은 없었다.

## 운영 보완

- 소켓 타임아웃을 20초에서 45초로 늘렸다. 소켓 타임아웃과 전체 실행시간은 다르므로 요청 시작 시 남은 예산을 최소 50초 확보한다. 기존 180초 예산과 워크플로 210초 강제 종료 제한을 보존한다.
- 정상 success 응답에 stockAvailable=false, stockError 없음, 전체 응답 목록의 수량이 미확인인 경우에는 상품·점포코드·매장명·주소·응답 개수 검증을 모두 통과해야 '검증된 미확인'으로 처리한다. 이는 공급자 통신 실패가 아니므로 연속 오류 회로를 열지 않는다. 수량은 null이며 0을 만들지 않는다. 기본 엄격 분류기의 기존 동작은 유지하고 운영 감시에서만 이 선택 동작을 사용한다.
- false 가용성 플래그와 비음수 숫자 수량이 함께 오면 모순으로 거부한다. 상품 불일치·점포 정체성 불일치·잘린 페이지·HTTP 오류는 계속 실패로 처리한다.
- 검증 실패 세부 코드, 요청 경과 시간, READ_TIMEOUT/NETWORK_ERROR 구분을 상태의 calls에 저장한다. 이번 실행 로그의 포괄적 UNVERIFIED_RESPONSE 원인을 추측해 단정하지 않는다.
- 요청 최대 6회, 오류 연속 2회 중단, 400/401/403/404/429 즉시 중단, 리디렉션 금지, 미확인 점포 순환 조회 및 대기 정책은 보존한다.

## 검증과 한계

오프라인 테스트 45개 통과. 정상 미확인 응답이 회로를 열지 않는지, 모순된 수량/상품이 계속 차단되는지, 45초 설정, 시간 예산, 실패 세부 기록을 검증했다. 실제 3회 재확인에서는 숫자 수량을 확보하지 못했다. 이전에 확인한 0을 현재 수량으로 재사용하지 않는다.

이 보완은 정상 응답을 너무 일찍 포기하거나 수량 미확인 응답을 공급자 장애로 잘못 세는 문제를 줄인다. 현재 API 경로에서 실제 수량을 받으려면 릴레이가 정상 수량 응답을 반환해야 한다. 다른 경로로 우회하거나 공식 API 연결이 완료됐다고 주장하지 않는다. 기존 CU·GS25·이마트24, 운영 재고 상태 및 알림 기준 파일은 변경하지 않는다.
